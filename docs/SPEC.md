# 뱀 달리기 게임 v0.1 — Codex 개발 지시서

## 1. 프로젝트 목표

플레이어가 직접 그린 뱀으로 100m 달리기 및 다양한 코스에서 경쟁하는 캐주얼 물리 기반 웹게임을 개발한다.

참고 게임:
https://hedorobomb.com/game/rakugaki-kengo/?k=Y2Q2C5

참고 게임의 핵심인 **사용자가 직접 그린 그림이 실제 게임 오브젝트가 되고, 그림의 형태가 움직임과 성능에 영향을 주는 구조**를 뱀 달리기 게임에 적용한다.

참고 게임의 그래픽이나 UI를 복제하지 말고 게임 메커니즘만 참고한다.

최종적으로 플레이어가 그린 뱀이 실제로 꿈틀거리며 다른 뱀들과 경쟁해야 한다.

게임은 모바일과 PC에서 동작하는 반응형 웹게임으로 개발하며, 별도의 유료 서비스나 외부 AI API 없이 작동하도록 한다.

기존 프로젝트가 존재하면 현재 파일, 기술 스택, 구현 상태를 먼저 분석한다. 이미 구현된 기능은 보존하고 필요한 부분만 수정한다. 프로젝트가 없다면 신규 프로젝트로 구성한다.

## 2. 핵심 확정 요구사항

### 뱀 제작

뱀을 반드시 세 단계로 나누어 그린다.

1. 머리 자유 그리기
2. 몸통 자유 그리기
3. 꼬리 자유 그리기

각 단계의 그림은 별도 데이터로 보존한다.

제작 완료 후 세 부분을 자동으로 연결하여 하나의 뱀을 구성한다.

플레이어가 그린 원래 형태와 개성을 최대한 유지해야 한다.

### 경기 방식

기본 조작 방식은 **자동 달리기**로 한다.

경기 준비 화면에 '조작 전환' 버튼을 배치한다.

- 기본값: 자동
- 버튼 클릭: 수동으로 전환
- 다시 클릭: 자동으로 전환
- 현재 방식은 화면에서 명확하게 표시
- 경기 시작 후에는 조작 전환 불가
- 경기 준비 화면에 새로 진입하면 기본값은 자동

자동 모드에서는 플레이어가 개입하지 않아도 뱀이 실제 물리 규칙과 능력치에 따라 달린다.

수동 모드에서는 플레이어의 입력이 같은 물리 엔진에 반영된다.

수동 조작이라고 해서 완전히 다른 경기 시스템을 사용해서는 안 된다.

## 3. 전체 게임 진행 흐름

메인 화면
→ 내 뱀 만들기 또는 저장된 뱀 선택
→ 머리 그리기
→ 몸통 그리기
→ 꼬리 그리기
→ 조립 및 움직임 미리보기
→ 경기 준비 화면
→ 경기 종류 선택
→ 자동/수동 조작 선택
→ 경주 시작
→ 카운트다운
→ 경기 진행
→ 결승선 통과
→ 결과 화면
→ 다시 달리기 / 뱀 수정 / 다른 코스 선택

경기 준비 화면과 실제 경주 화면의 완성도를 우선한다.

# 4. 경기 준비 화면 상세 구현

## 4.1 기본 화면 구조

상단:
- 뒤로 가기
- 화면 제목: 경기 준비
- 선택된 뱀 이름

중앙 상단:
- 내가 그린 뱀의 실제 모습
- 부드러운 대기 애니메이션
- 뱀 수정 버튼

중앙:
- 경기 종류 선택
- 참가 선수 미리보기
- 조작 방식 선택
- 경기 간단 정보

하단:
- 경주 시작 버튼

모바일에서는 하단 시작 버튼이 항상 접근 가능한 위치에 있도록 한다.

PC에서는 화면을 적절한 최대 너비로 제한하여 지나치게 넓어지지 않도록 한다.

## 4.2 내 뱀 미리보기

플레이어가 직접 제작한 뱀을 화면 중앙에 표시한다.

요구사항:
- 머리·몸통·꼬리가 연결된 상태로 렌더링
- 실제 손그림의 색상과 외형 유지
- 제자리에서 약하게 꿈틀거리는 애니메이션
- 뱀 이름 표시
- 뱀 수정 버튼
- 필요한 경우 가속력, 최고 속도, 안정성 등 간단한 능력치 표시

미리보기에서 사용하는 애니메이션 구조는 실제 경주 엔진과 최대한 공유한다.

## 4.3 경기 종류 선택

경기 카드를 표시한다.

**100m 달리기**
- 기본 선택
- 직선 트랙
- 4마리 동시 출전
- 개별 레인 사용
- 가속력과 최고 속도가 중요한 경기

**코스 달리기**
- 장애물과 지형 변화가 있는 경기
- 경사로, 물웅덩이, 작은 장애물 등을 지원하도록 확장 가능한 구조

v0.1에서는 100m 달리기의 실제 완성을 우선한다.

코스 달리기를 완전히 구현하지 못했다면 플레이 가능한 것처럼 표시하지 않는다. 미구현 상태를 명확하게 표시하거나 실제 구현 완료 후 활성화한다.

## 4.4 참가 선수

기본 4마리:
- 플레이어 뱀 1마리
- CPU 뱀 3마리

각 참가자의 이름, 외형, 색상을 표시한다.

CPU도 머리·몸통·꼬리 구조를 갖는 뱀으로 생성한다.

CPU는 각자 다른 신체 구조와 능력치를 가지되, 플레이어와 같은 물리 규칙을 사용한다.

참가자 데이터는 확장 가능하게 관리한다.

## 4.5 조작 전환 버튼

이 화면의 핵심 기능이다.

초기 상태:

현재 조작: 자동 달리기

[조작 전환]

버튼을 누르면:

현재 조작: 수동 달리기

[자동으로 전환]

자동 설명:
'뱀이 자신의 능력치와 물리 규칙에 따라 자동으로 달립니다.'

수동 설명:
'직접 입력하여 뱀의 추진을 조절합니다.'

전환 시 선택 상태와 설명이 즉시 변경되어야 한다.

전환에 확인 팝업은 필요 없다.

조작 방식은 경기 시작 시 확정하며, 경기 진행 중에는 변경할 수 없다.

# 5. 실제 100m 경기 화면

## 5.1 화면 구성

화면은 실제 경주를 보여주는 트랙을 중심으로 구성한다.

상단 HUD:
- 경기명: 100m 달리기
- 실시간 경기 시간
- 현재 순위
- 이동 거리 / 100m
- 경기 일시정지 버튼

중앙:
- 수평으로 이어지는 100m 트랙
- 4개 레인
- 각 레인에서 움직이는 뱀
- 뱀 이름 또는 식별 표시
- 시작선과 결승선
- 부드러운 카메라 이동

하단:
- 내 뱀의 진행률
- 자동 모드에서는 관전 정보만 표시
- 수동 모드에서는 조작 컨트롤 표시

불필요한 화면 장식과 과도한 효과는 배제한다.

## 5.2 트랙 표현

기본적으로 2D 횡스크롤 형태를 사용한다.

100m 전체를 한 화면에 억지로 압축하지 않는다.

뱀의 형태와 꿈틀거리는 움직임을 충분히 볼 수 있는 확대 배율을 적용한다.

카메라는 내 뱀의 진행 위치를 중심으로 부드럽게 이동한다.

다른 CPU 뱀도 같은 좌표계에서 이동해야 한다.

뱀 간 거리 차이는 실제 진행 거리 차이를 반영해야 한다.

게임 화면에 나타나는 순위와 트랙 위 실제 위치가 일치하도록 한다.

트랙의 시작점, 25m, 50m, 75m, 100m 지점을 시각적으로 구분한다.

## 5.3 경기 시작

경주 시작 버튼을 누르면 경기 준비 상태를 확정한다.

화면 전환 후 다음 카운트다운을 실행한다.

3 → 2 → 1 → GO!

GO 이전에는 모든 참가자가 움직이지 않아야 한다.

GO 이후 동일한 시뮬레이션 기준 시점에서 경주가 시작되어야 한다.

중복 클릭으로 경기가 두 번 생성되지 않도록 방지한다.

## 5.4 자동 달리기

자동 모드에서는 플레이어의 추가 입력 없이 경기가 진행된다.

뱀의 이동은 다음 요소를 반영한다.

- 몸통 길이
- 몸통 굴곡
- 몸통 유연성
- 머리 및 꼬리 형태
- 가속력
- 최고 속도
- 지구력
- 지면 마찰
- 몸통 파동에 의한 추진

자동 달리기는 단순히 이미지를 오른쪽으로 이동시키는 방식으로 구현하지 않는다.

몸통이 구불거리며 진행하고, 머리와 꼬리가 몸통 움직임을 따라 자연스럽게 반응해야 한다.

뱀마다 움직임의 특성이 달라야 한다.

다만 모든 참가자에게 동일한 물리 규칙과 제한을 적용한다.

승자를 사전에 지정하지 않는다.

경주 결과는 실제 시뮬레이션 결과로 결정한다.

## 5.5 수동 달리기

경기 준비 화면에서 수동을 선택한 경우에만 조작 컨트롤을 표시한다.

100m 경기의 기본 수동 조작은 좌우 입력을 번갈아 사용하는 리듬 추진 방식으로 구현한다.

모바일:
- 화면 하단 좌측 추진 버튼
- 화면 하단 우측 추진 버튼
- 좌우 번갈아 터치하면 추진력이 발생

PC:
- A / D 또는 좌우 방향키 입력

수동 모드에서도 몸통 관절 애니메이션과 물리 규칙을 동일하게 적용한다.

연타 속도가 빠르다는 이유만으로 무한 가속하지 않도록 한다.

입력 간격, 몸통의 추진 주기, 최대 속도를 반영한다.

입력이 없는 경우 자연스럽게 감속하도록 한다.

수동 조작이 자동 모드보다 항상 유리하거나 불리하지 않도록 기본 밸런스를 조정한다.

## 5.6 경기 중 상호작용

자동 모드에서 가능한 기능:
- 경기 관전
- 일시정지
- 재개
- 경기 재시작
- 경기 종료

수동 모드에서 가능한 기능:
- 좌우 추진 조작
- 일시정지
- 재개
- 경기 재시작
- 경기 종료

일시정지 시:
- 경기 시간 정지
- 물리 시뮬레이션 정지
- 애니메이션 정지
- 사용자 조작 입력 무시

재개 시:
- 중복 경기 루프 생성 금지
- 기존 경기 상태 유지

재시작 시:
- 진행 거리 초기화
- 경기 시간 초기화
- 선수 위치 초기화
- 물리 상태 초기화
- 동일한 경기 설정 유지

경기 종료를 선택하면 확인 팝업을 표시하고 경기 준비 화면으로 돌아간다.

경기 중 새로고침 또는 화면 이탈 시에도 오류가 발생하지 않도록 자원을 정리한다.

# 6. 손그림 뱀 물리 시스템

## 6.1 그림 데이터

머리, 몸통, 꼬리를 별도 데이터 구조로 관리한다.

각 부위에는 다음 정보가 필요하다.

- 원본 그림 데이터
- 외형 경로
- 색상 정보
- 연결 지점
- 기준 좌표
- 크기 정보
- 충돌 형태

몸통에는 추가로 다음 정보를 관리한다.

- 중심선
- 관절 위치
- 관절 간 거리
- 전체 길이
- 굴곡 정도
- 유연성

## 6.2 조립

머리와 몸통, 몸통과 꼬리를 지정된 연결 지점으로 결합한다.

사용자가 그린 외형을 최대한 유지하면서 크기와 방향을 조정한다.

경주 중 각 부위가 분리되지 않도록 처리한다.

특이한 모양이나 불규칙한 그림도 오류 없이 처리해야 한다.

자동 연결이 실패할 경우 사용자가 연결 위치를 지정하거나 기본 연결 위치를 적용할 수 있도록 한다.

## 6.3 몸통 애니메이션

몸통을 여러 개의 연결된 관절로 표현한다.

추진 시 몸통을 따라 파동이 전달되도록 한다.

각 관절은 일정한 거리 제약을 유지해야 한다.

머리의 진행 방향과 몸통 곡률이 연결되어 자연스럽게 움직여야 한다.

꼬리는 몸통 움직임에 따라 후방에서 흔들려야 한다.

그림을 단순히 늘리거나 좌우로 흔드는 가짜 애니메이션만 적용하는 것은 허용하지 않는다.

다만 완전한 생체역학 시뮬레이션보다는 게임 플레이의 안정성과 자연스러운 표현을 우선한다.

물리 연산과 렌더링을 분리하고 고정 시간 간격 기반 시뮬레이션을 사용한다.

## 6.4 성능 밸런스

무조건 길거나 굵게 그리는 것이 유리하지 않도록 한다.

모든 몸통을 단순한 동일 크기로 바꾸지는 않는다.

서로 다른 체형의 장단점을 유지해야 한다.

극단적인 형태, 매우 작은 그림, 자기 교차가 많은 그림 등을 처리할 안전한 기준을 마련한다.

능력치에는 상한과 하한을 설정한다.

경주 성능은 체형뿐 아니라 마찰, 추진 주기, 안정성 등 여러 요소가 함께 결정하도록 한다.

# 7. 경기 HUD 및 실시간 상태

경기 진행 중 다음 정보를 실시간으로 계산한다.

- 경과 시간
- 현재 속도
- 현재 이동 거리
- 현재 순위
- 참가자별 진행 거리
- 결승선 통과 여부

진행률은 0~100% 범위로 제한한다.

현재 순위는 모든 참가자의 실제 이동 거리를 기준으로 갱신한다.

화면에 표시되는 시간은 시뮬레이션 시간과 동기화한다.

브라우저 프레임률 차이로 경주 결과가 크게 달라지지 않도록 처리한다.

결승선을 통과한 참가자는 실제 통과 시점을 보간하여 기록을 계산한다.

완주 판정은 뱀의 머리 끝이 아니라 지정한 몸통 기준점이 결승선을 통과했을 때로 통일한다.

---

# 8. 경기 종료 및 결과 화면

모든 참가자가 완주하거나 경기 종료 조건이 충족되면 결과 화면으로 전환한다.

표시 항목:
- 경기 종류
- 조작 방식
- 최종 순위
- 100m 완주 기록
- 참가자별 완주 시간
- 최고 속도
- 기존 개인 최고 기록과 비교
- 새로운 기록 달성 여부

버튼:
- 다시 달리기
- 내 뱀 수정
- 다른 코스 선택
- 메인 화면

모든 버튼은 실제로 동작해야 한다.

다시 달리기는 같은 뱀과 경기 설정으로 새 경기를 시작할 수 있어야 한다.

기록은 로컬에 저장한다.

자동 경기와 수동 경기의 최고 기록은 별도로 관리한다.

# 9. UI/UX 디자인

## 전체 디자인 방향

귀엽고 가벼운 캐주얼 웹게임을 지향한다.

손으로 그린 뱀이 게임의 주인공이므로, 캐릭터의 형태와 움직임을 가장 중요하게 표현한다.

디자인 요구사항:

- 모바일 우선 반응형
- PC에서도 자연스러운 레이아웃
- 손그림 느낌과 어울리는 그래픽
- 간결하고 명확한 버튼
- 높은 텍스트 시인성
- 따뜻하고 부드러운 색상
- 과도한 그라데이션 금지
- 불필요한 빛 효과 금지
- 과장된 3D 효과 금지
- 게임에 집중하기 어려운 복잡한 HUD 금지
- 모바일 터치 영역 충분히 확보

권장 스타일:
- 아이보리 또는 밝은 뉴트럴 UI
- 부드러운 그린과 오렌지 포인트
- 경쾌한 트랙 색상
- 단순한 2D·2.5D 게임 그래픽
- 자연스러운 움직임과 절제된 이펙트

PC에서는 키보드 조작과 마우스 사용을 지원하고, 모바일에서는 터치 기반 인터페이스를 적용한다.

# 10. 기술 및 저장 구조

권장 기술:
- React
- TypeScript
- Canvas 기반 그리기
- Canvas/WebGL 기반 경기 렌더링
- 로컬 2D 물리 또는 자체 관절 시뮬레이션
- localStorage 또는 IndexedDB
- 반응형 CSS

기존 프로젝트에 적합한 기술 스택이 있다면 이를 우선 활용한다.

무료 오픈소스 라이브러리 사용은 가능하다.

필수 조건:
- 외부 AI API 불필요
- 유료 서버 불필요
- 로그인 없이 플레이 가능
- 로컬 플레이 지원
- PC 및 모바일 지원
- 기존 소스와 호환성 유지

프로젝트 내 모듈은 그림 입력, 뱀 데이터, 형태 분석, 관절 물리, 경기 시뮬레이션, CPU 제어, UI 및 기록 저장이 분리되도록 설계한다.

향후 코스 추가 및 CPU 증가를 고려하되, 불필요한 대규모 아키텍처를 만들지는 않는다.

# 11. 테스트 및 검증

다음 항목을 실제로 검증한다.

### 뱀 제작
- 머리·몸통·꼬리를 각각 그릴 수 있는가?
- 세 부분이 정상적으로 조립되는가?
- 원본 그림의 형태가 보존되는가?
- 부위별 수정 및 재저장이 가능한가?
- 특이한 모양에서도 오류가 발생하지 않는가?

### 경기 준비
- 기본 조작이 자동인가?
- 버튼을 누르면 수동으로 변경되는가?
- 다시 누르면 자동으로 변경되는가?
- 현재 선택이 정확하게 표시되는가?
- 시작 버튼이 실제 경주를 실행하는가?
- 미구현 경기 모드를 실행 가능한 것처럼 표시하지 않는가?

### 경기 진행
- 카운트다운이 정상 작동하는가?
- 4마리의 뱀이 동시에 출발하는가?
- 플레이어 뱀이 실제로 전진하는가?
- 몸통과 꼬리가 자연스럽게 움직이는가?
- 뱀의 형태에 따라 움직임과 성능이 달라지는가?
- CPU가 독립적으로 달리는가?
- 경기 시간이 정상적으로 증가하는가?
- 거리와 순위가 실제 위치와 일치하는가?
- 일시정지 및 재개가 정상 동작하는가?
- 자동 모드에 불필요한 조작 버튼이 없는가?
- 수동 모드에서 실제 입력이 적용되는가?
- 수동 모드에서 조작하지 않을 경우 감속하는가?
- 경기 시작 후 조작 방식을 바꿀 수 없는가?

### 경기 종료
- 결승선 통과가 정확하게 판정되는가?
- 경기 결과와 실제 주행이 일치하는가?
- 기록이 정상 저장되는가?
- 재경기를 정상 실행하는가?
- 기록이 자동·수동으로 구분되는가?

### 안정성
- PC와 모바일에서 정상 렌더링되는가?
- 화면 크기를 변경해도 레이아웃이 깨지지 않는가?
- 일시정지·재시작 반복 시 중복 루프가 없는가?
- 메모리 누수 및 주요 런타임 오류가 없는가?
- 낮은 프레임률에서도 물리 결과가 안정적인가?

가능한 항목은 자동화 테스트로 검증하고, 시각적 판단이 필요한 항목은 실제 화면에서 검증한다.

# 12. 개발 우선순위

1. 기존 프로젝트 상태 파악 및 필요한 변경 범위 결정
2. 뱀 머리·몸통·꼬리 데이터 구조 구현
3. 그림 조립 및 움직임 미리보기 구현
4. 실제 몸통 관절 애니메이션 및 이동 엔진 구현
5. 100m 트랙과 CPU 3마리 구현
6. 경기 준비 화면 완성
7. 자동/수동 전환 구현
8. 경기 HUD 및 카메라 추적 구현
9. 경기 일시정지·재시작·종료 구현
10. 결승선 판정 및 결과 화면 구현
11. 로컬 기록 저장
12. 모바일 및 PC 테스트와 UI 개선

단순히 화면과 버튼만 구현하는 것으로 완료 처리하지 않는다.

**반드시 실제로 움직이는 뱀과 끝까지 진행되는 100m 경기를 구현한다.**

우선순위가 충돌하면 100m 경기의 완성도를 우선하고, 코스 레이스 등 추가 요소는 확장 가능한 구조로 준비한다.
